# Decisions (ADR-lite)

Append new entries at the bottom. Format: context → decision → consequences.

## ADR-001 Build from scratch instead of forking pg-view
pg-view has no public source repository (only a Docker image), no user model and
no SSO. Requirements (Entra SSO, cluster discovery, per-group authz, audit) touch
every layer. → Build our own; pg-view is the functional reference only.

## ADR-002 Go backend + React SPA in one binary
Team strength is Go; single static binary simplifies deployment and image
hardening. SPA embedded via `go:embed`. No SSR.

## ADR-003 SQLite (modernc) as app store, single replica
Store holds sessions, history, favorites, drafts, ui state, audit. Volume is
small. SQLite avoids an extra dependency inside the cluster and keeps the app
self-contained. → `replicas: 1`, `Recreate` strategy, PVC.
Consequence: no HA; brief downtime on upgrades. Audit is also shipped to stdout
so loss of the PVC does not lose the audit trail. A Postgres store backend can be
added later behind the `store.Store` interface (keep it an interface from day 1).

## ADR-004 Fetch all results in Postgres TEXT format
Avoids per-type JSON mapping bugs (numeric precision, int8 > 2^53, intervals,
ranges, composite, custom enums, arrays). UI shows exactly what psql shows.
Writes send text and cast server-side with `$n::<format_type>`.
Consequence: no client-side numeric sorting of results (grid sorting is
server-side anyway).

## ADR-005 Secrets: `get` only, no list/watch
Listing/watching Secrets would load every secret of target namespaces into
memory. Discovery only needs names (from pod specs/CR conventions); values are
fetched by `GET` at pool creation. RBAC grants `get` on secrets only.

## ADR-006 Explicit namespace list, no cluster-wide discovery
Least privilege and predictable blast radius. Namespaced Roles generated by the
Helm chart per listed namespace. No ClusterRole for workloads/secrets.
*Superseded by ADR-024* (cluster-wide by default, the list is optional).

## ADR-007 No Microsoft Graph in v1
Groups taken from the ID token only; overage rejected with instructions to use
`ApplicationGroup` claims. Avoids Graph permissions/consent. Revisit if needed.

## ADR-008 Statement classification with libpg_query (wasm, pure Go)
Regex-based detection of destructive SQL is unreliable (CTEs, comments,
quoting). `github.com/wasilibs/go-pgquery` gives the real Postgres parser
without cgo.

## ADR-009 One statement per editor execution
Simplifies classification, confirmation, cancel, result shaping and audit.
Multi-statement scripts are a possible v2 feature.

## ADR-010 Authorization in the app, plus optional read-only DB role
Discovered credentials are usually owner/superuser. App-level rules + READ ONLY
transactions are the baseline; a dedicated read-only Postgres role referenced
via annotation is the recommended hardening for production targets.

## ADR-011 Reset editor connections with DISCARD ALL; exec mode without statement cache
User SQL can change session state that survives the transaction even in READ
ONLY mode (`set_config(..., false)`, `pg_advisory_lock`, temp tables, `SET ROLE`
via `set_config('role', ...)`). On a shared pool this leaks into the next
user's request. → After every editor execution run `DISCARD ALL` before the
connection is released; destroy the connection if that fails. Pools use
`pgx.QueryExecModeExec` (unnamed statements, text results), so `DISCARD ALL`
never invalidates a client-side prepared statement cache.
Consequence: one extra round trip per editor query; no prepared statement reuse.

## ADR-012 Target addressed by two path segments, not an encoded `/`
`ns%2Fname` in a path is decoded, rejected or normalized by many ingress
controllers and load balancers. Namespace and name are DNS-1123 labels and can
never contain `/`. → API paths use `/targets/{ns}/{name}/...` and
`/drafts/{ns}/{name}/{db}`. The JSON field `id` stays `<ns>/<name>`.

## ADR-013 Reject statements that cannot run in a transaction block (v1)
Hard rule 4 runs every statement in a transaction with `SET LOCAL` guards.
VACUUM, CREATE/DROP DATABASE, `... CONCURRENTLY`, ALTER SYSTEM etc. fail there
with a confusing server error. → `sqlclass` marks them `nontx` and the editor
returns 400 `unsupported_statement` with an explanatory message. Running them
outside a transaction with session-level guards is a possible v2 feature.

## ADR-014 Side-effect function denylist for read level
READ ONLY transactions still allow `pg_terminate_backend`, `pg_reload_conf`,
`lo_export`, `dblink`, `set_config`, advisory locks. Discovered credentials are
usually owners/superusers. → `sqlclass` walks the whole parse tree; any call to
a function in the SPEC §7.2 list makes the statement `dml`, so `read` users get
403. It is a denylist (defense in depth); a read-only DB role (ADR-010) stays
the strong control.

## ADR-015 CSRF protection for logout
`POST /auth/logout` lives outside `/api` and was not covered by §5.4. A forced
logout is low impact but trivial to prevent. → The SPA submits a regular form
(full-page navigation is needed for the Entra redirect) with a hidden `csrf`
field; the server checks it plus Origin before deleting the session.

## ADR-016 No Pods informer / RBAC
Discovery works from StatefulSets, Deployments, Services and operator CRs; the
headless fallback derives `<sts>-0` from the StatefulSet name. Operator-owned
pods only matter for CNPG, which creates no StatefulSets the generic source
could see. → Do not watch pods; Roles grant no access to pods.

## ADR-017 Credential references as value sources; workload names; ConfigMap get
DISCOVERY §1 modelled credentials as one Secret with optional fixed user, or a
literal-env pointer. Real workloads mix sources (user literal, password from a
Secret; user from a ConfigMap; `_FILE` on a projected volume; database from
an envFrom Secret). → `CredentialRef{User, Password ValueSource}` where a
`ValueSource` is exactly one of `literal` (non-secret values only), `secret`
(name+key), `configMap` (user/db only) or `env` (pointer to a literal env var in
the pod template, read from the informer cache at connect time). The database
for the first connection is `defaultDB` or `defaultDBFrom` (a value source,
e.g. "same as the user secret key") resolved at connect time, else `postgres`.
Target names for workload-based targets are the workload name (the §3 collision
rule with `-sts`/`-deploy` suffixes only makes sense that way); annotated
Services and operator CRs use their own name. Colliding targets all get the
suffix so no target silently takes over a name.
Consequence: resolving a user or database from `envFrom.configMapRef` /
`configMapKeyRef` needs `configmaps: get` in the per-namespace Role (still no
list/watch).

## ADR-018 Bind grid values with the column's type OID instead of `::type` casts
ADR-004 and SPEC §8 describe `col = $1::<format_type>`. That embeds a type
name string from the catalog into generated SQL (not an identifier that
`pgx.Identifier.Sanitize` can handle). → Values are sent as text bind
parameters whose parameter type OID is the column's type (`= ANY($n)` uses
`pg_type.typarray`), so the server parses them with the column's input function
exactly as a cast would. `like/ilike` compare `col::text`. Generated SQL then
contains only sanitized identifiers, fixed keywords and `$n` placeholders. The
same applies to grid writes (M7).

## ADR-019 Aegean visual design
The first UI used Gruvbox with a top bar of selects and emoji glyphs; it read
as a hobby tool. The owner asked for something premium but plain, using
pg-view as the functional reference without copying its look. → Aegean theme:
marble/limestone neutrals, one Aegean-blue accent, laurel gold reserved for
environment warnings (the production ring on the connection card is the single
loud element). IBM Plex Sans for UI and Plex Mono for data (self-hosted via
@fontsource, so the CSP stays `default-src 'self'`), lucide icons. Layout: no
top bar; the sidebar carries brand, connection card, ⌘K table search, tree and
the user row; the main area has tabs and a `Data | Structure | SQL` segmented
control per table. Light, dark and "match system" themes are tokens in
`web/src/styles/theme.css`.
Dark theme ("Aegean night", revised after review): the first dark palette was
a saturated navy with weak contrast. It is now a neutral charcoal
(`#111214`/`#18191c`) with the Aegean blue only as accent; solid fills use a
darker `--accent-fill` / `--danger-fill` so white labels pass WCAG AA, and
body/secondary/tertiary text measure 14.2 / 7.2 / 4.7:1 on the surface. Theme
tokens carry no colour transitions: Safari kept stale colours on transitioned
elements after a theme switch.
Brand (replaces an interim column icon): the owner's brand sheet, redrawn
as clean SVG in `docs/assets/brand/`. A rounded heptagon with a helm wheel,
a Slonik-style elephant and a database stack, navy/blue/cyan palette, the
"Athens" wordmark in Poppins Bold (as paths) with a swoosh. Icon, favicon
(simplified for 16/32 px), light/dark lockups, mono marks and the social
preview. The motifs echo the Kubernetes wheel and the PostgreSQL elephant;
both are third-party marks (CNCF, PostgreSQL Community Association), so
clear their use with the owners' trademark policies before any commercial
or trademark use of the logo. The UI theme is Gruvbox since ADR-025.

## ADR-020 Discovery is opt-in (annotation-only) by default
Automatic discovery showed every postgres-looking workload in the listed
namespaces, including scratch databases and copies nobody meant to expose.
The owner wants exposure to be an explicit decision per database. →
`discovery.requireAnnotation: true` (default): only StatefulSets,
Deployments, Services, CNPG Clusters and Zalando postgresqls annotated
`athens.warewave.io/enabled: "true"` become targets. One annotation is enough:
credential resolution from the container env (§4.4) and from operator secrets
(§4.2, §4.3) still works for annotated objects, so teams don't have to copy
secret names into annotations. `requireAnnotation: false` restores automatic
discovery. RBAC is unchanged (list/watch is needed to read the annotations).

## ADR-021 Reads, admin views and user items are audited
The first audit trail covered sign-ins, editor executions and grid writes
only, so browsing a table in the grid left no trace although an editor
`SELECT` did. → With `audit.logReads: true` (default) every grid page
(`rows_read`), full cell value (`cell_read`) and structure view
(`structure_view`) is recorded with target, database and `schema.relation`.
Grid filter values are kept only with `audit.logValues` (they can be the
sensitive data itself); primary keys of cell reads are kept, as they already
are for row updates. Schema/relation listings and completion are navigation
metadata and are not recorded. Saved query create/update/delete and history
deletes are recorded (SQL in the `sql` field, subject to `logSQL`); drafts and
UI state are autosaved per keystroke and are not. Admin page views are
recorded as `admin_view`, throttled in memory to one per user, page and
filter set every 5 minutes because the pages poll; "load more" pages of the
audit view are the same view. Admins can export the filtered log as CSV or
JSON Lines (capped at 100 000 records, export audited, CSV formula cells
prefixed with `'`). The SQLite copy stays app-level tamper-resistant only;
OPERATIONS.md documents shipping the stdout copy to append-only storage.

## ADR-022 Per-target access from annotations
The owner wants the team that runs a database to decide, next to the
database, that it is read-only and who may use it, without a change to the
athens config. → Two annotations on the discovered object:
`<prefix>/readonly: "true"` caps every user at read on that target, and
`<prefix>/access: "group:rw,group:ro"` replaces `authz.rules` for that target
(authoritative, not additive: "the groups that can access this database").
With both, everyone on the list is read-only. Fail closed everywhere: an
unparsable `readonly` value means read-only, invalid access entries are
dropped, and an access list that grants nobody hides the target. Groups are
matched as Entra group IDs or through `authz.groupAliases` names, since tokens
carry IDs. Trust: whoever can annotate workloads in a watched namespace can
grant access to that database through athens; in practice the same people can
already read its Secret. Platform teams that do not accept this set
`authz.annotationAccess: false` (the `access` annotation is then ignored and
shown as such on Admin → Discovery; `readonly` still applies because it only
removes rights). The global `authz.readOnly` switch and admin-has-no-data
rules are unchanged.

## ADR-023 Access only from the access annotation
ADR-022 let the `access` annotation override `authz.rules`. The owner wants
one place for access, next to the database: the team that runs a database
decides who uses it. → `authz.rules` and `authz.annotationAccess` are removed.
A target's level is the highest grant of its `<prefix>/access` annotation for
the user's groups (IDs as in the token, or `authz.groupAliases` names),
capped by `readonly` and the global `authz.readOnly`. A target without the
annotation is usable by nobody (fail closed) and shows a warning on Admin →
Discovery; admins still get no data access by being admins. The annotation
covers every database of a target: the per-database globs of the old rules
are gone. The configuration keeps only `adminGroups`, `readOnly` and
`groupAliases`. Old configs fail at start with a message naming the
replacement instead of silently losing access. Supersedes the
"replaces the rules" part of ADR-022.

## ADR-024 Discovery is annotation-only and cluster-wide by default
With access on the annotation (ADR-023) a namespace list in the athens
config is one more thing to keep in sync, and automatic image-based discovery
can no longer yield usable targets. → `discovery.requireAnnotation` and the
`generic` source are removed: only objects annotated `<prefix>/enabled: "true"`
become targets, and `discovery.imagePattern` only picks the postgres
container of an annotated workload. `discovery.namespaces` becomes optional:
empty (default) watches the whole cluster with one informer set; the chart
then creates a ClusterRole (statefulsets/deployments/services/CRDs
get-list-watch, secrets/configmaps **get only**) and the NetworkPolicy allows
Postgres egress to every namespace. Listing namespaces restores the
namespaced Roles of ADR-006. Trade-off: athens can `get` a Secret in any
namespace, but only reads those referenced by annotated objects in the same
namespace; clusters that need a hard boundary list namespaces. Namespaces
without targets or problems are left off the admin status list. Supersedes
ADR-006 and the opt-out/automatic mode of ADR-020.

## ADR-025 Gruvbox theme with an aqua accent
The owner preferred the Gruvbox look over Aegean (ADR-019). After a
side-by-side preview of the dark and light modes with four accents, aqua
was chosen. → `web/src/styles/theme.css` maps the Gruvbox palette onto the
existing tokens: bg0/bg0_h/bg0_s for page, surfaces and sidebar, fg1-fg4
for text, aqua (`#427b58` light, `#8ec07c` dark) as the accent, orange as
the production colour (the `--laurel-*` tokens keep their name), red for
danger, Gruvbox syntax colours in the editor. Solid light-mode buttons use a
darker aqua (`#376a4b`) so cream labels pass WCAG AA (5.6:1); dark mode puts
`#282828` text on `#8ec07c` (7:1). Layout, components, IBM Plex fonts and the
brand logo are unchanged. Supersedes the palette part of ADR-019.

## ADR-026 Read-only role without a read-only login
Many databases have no read-only login, and env-discovered ones usually run
on the `postgres` superuser. READ ONLY transactions plus statement
classification stop writes, but read users still carried the superuser's
read privileges: server files (`pg_read_file`, `pg_ls_dir`), other
sessions' queries, role password hashes. → When a read user runs on the RW
login, every transaction does `SET LOCAL ROLE` to the `readonly-role`
annotation or, by default, `pg_read_all_data` (PostgreSQL 14+). The first
transaction per target checks, inside a savepoint, that the role exists and
the login is a member; the result is cached until the target changes. If no
role is usable (PostgreSQL 13, a non-member login), athens keeps READ ONLY
transactions and warns admins instead of refusing service. `SET LOCAL` ends
with the transaction, `RESET ROLE`/`SET ROLE`/`set_config('role')` are
already rejected by sqlclass, and editor sessions are `DISCARD ALL`-ed.
*Amended by ADR-027:* functions that run SQL as text could reset the role,
so on privileged logins the role switch is not treated as a boundary.
`pg_read_all_data` can still read `pg_authid`, so independently of the role
the credential catalogs (`pg_authid`, `pg_shadow`, `pg_user_mapping(s)`) are
refused for everyone in the editor (classified as session statements) and
the grid (404). Writers never switch roles. A dedicated read-only login
(`readonly-secret`) stays the strongest option.

## ADR-027 Security review before 0.1.3
An internal review (scanners plus two independent code reviews, every
finding confirmed against Postgres 16 and 13) found, and this release fixes:
- **Dynamic SQL escaped the classifier (critical).** `query_to_xml`,
  `table_to_xml`, `schema_to_xml`, `database_to_xml`, `cursor_to_xml`,
  `ts_stat`, `ts_rewrite` run SQL given as a string, so a read user could
  call anything, including `set_config('role', 'none')` to leave
  `pg_read_all_data`. → They are side-effect functions now, together with
  server file (`pg_read_file`, `pg_ls_*`, `pg_stat_file`), replication slot
  (`pg_replication_slot_advance`, `pg_copy_*`, `pg_logical_slot_*`), backup
  and large-object write functions (LO writes pass READ ONLY before PG14).
  Plain EXPLAIN is walked for functions and credential catalogs, because
  planning evaluates stable functions. NUL bytes are rejected.
- **No role boundary on privileged logins.** Any user-defined function with
  dynamic SQL can still `set_config('role', ...)` back to the login.
  Superuser, REPLICATION and BYPASSRLS logins therefore never serve read
  users' SQL editor without an RO login (403 `read_login_required`, admin
  warning); athens-generated SQL (grid, structure, catalog) keeps working
  under the role switch. Non-privileged logins keep ADR-026's warn-only
  fallback.
- **Writers' function side effects skipped confirmation.** Statements a
  writer runs that classify as read execute READ ONLY; a 25006 turns into a
  409 confirmation and the confirmed re-run is writable. MERGE and
  `WHERE ... OR true` are destructive.
- **More credential catalogs:** `pg_subscription` (connection strings with
  passwords), `information_schema._pg_user_mappings`, `user_mapping_options`,
  `_pg_foreign_servers`.
- **HTTP:** unknown methods are refused with 405 before routing (a raw
  method label created unbounded metric series, an unauthenticated OOM);
  read/header timeouts and a 64 KiB header limit; `--dev` needs insecureDev.
- **Audit:** every field is length-bounded; the export streams in pages and
  defuses formulas in every CSV cell; callbacks without sign-in state are
  counted, not audited (anonymous flooding).
- **Per-user storage caps:** 500 saved queries, 300 drafts (only for
  visible targets), 100 UI state entries; saved-query targets must be
  visible; database/schema/relation names over 63 bytes are 404.
- **Pools:** a missing explicit database returns 404 and drops its pool
  without marking the target unreachable; at most 32 pools per target (LRU).
- **Cookies:** `__Host-athens_session`, `__Host-athens_csrf` and
  `__Secure-athens_auth` (plain names only with insecureDev), so sibling
  subdomains cannot plant them; a new sign-in deletes the browser's previous
  session. Existing sessions end with the upgrade.
- **CSV downloads** in the UI defuse spreadsheet formulas (numbers stay).
- **Supply chain:** GitHub Actions pinned by commit SHA, tools pinned,
  govulncheck and pnpm audit in CI, Dependabot; Go toolchain 1.26.11,
  klauspost/compress 1.20.4, x/crypto 0.59.0; distroless debian13 base
  (debian12 carried outdated ca-certificates and tzdata); dev-only
  minimatch override.

A verification round on these fixes found and this release also fixes:
- *Privileged* means membership too: a login that is a member of a
  superuser/REPLICATION/BYPASSRLS role or of `pg_monitor`,
  `pg_read_all_settings`, `pg_read_all_stats`, `pg_signal_backend` or the
  server-file roles counts as privileged (a member of `postgres` could
  `SET ROLE postgres` through a dynamic-SQL function; `pg_monitor` reads
  `primary_conninfo`). The check runs for the RO login as well, per
  credential kind, and again whenever a pool is created.
- On a privileged login without a usable read role, read users are also
  refused grid rows (athens' own SELECTs would run with the login's
  privileges, e.g. `pg_settings`); structure and listings stay.
- `brin_summarize_*`, `brin_desummarize_range`, `gin_clean_pending_list`
  are side-effect functions (they change indexes inside READ ONLY).
- An unconfirmed DML statement that changes more than 1000 rows is rolled
  back and needs confirmation, which catches tautologies (`WHERE id = id`)
  the syntactic heuristic cannot.
- Explicit database names are checked against the cached database list
  before a pool is created; a database's own refusal (3D000, 42501) is 404
  or 403 and never marks the target unreachable; an evicted pool is retried.
- Sign-in callbacks with an invalid or mismatched state are never audited
  (counted and logged instead); per-user byte budget of 16 MiB for saved
  queries, drafts and UI state, history trimmed to 16 MiB of SQL; the
  export counts first, so `X-Athens-Export-Capped` is a real header, and a
  failed export is audited as `error`.

A third round fixed:
- Privilege is re-checked in every read transaction (a role granted later,
  e.g. `GRANT postgres TO app`, is seen immediately); only the role-switch
  usability is cached.
- The 1000-row rule counts the statement's real changes (difference of
  `pg_stat_xact_all_tables` around it), so writable CTEs, EXPLAIN ANALYZE,
  cascades and triggers are counted too; a column type change
  (`ALTER COLUMN ... TYPE`, with or without `USING`) is destructive.
- Sign-in failures before the ID token verifies (`idp_error`,
  `exchange_failed`, `invalid_id_token`, `invalid_nonce`) are counted and
  logged, not audited; denials of a verified user still are.
- The per-user budget counts bytes (`length(CAST(x AS BLOB))`), checks
  updates by their size difference (saved queries included), and a failed
  export aborts the download instead of ending it as if complete.

Residual, accepted: a user-defined function in the target database that
runs dynamic SQL can still switch an unprivileged login's role or send
NOTIFY without a confirmation; on unprivileged logins that grants nothing
beyond the login's own rights.

Accepted (documented in `.trivyignore`): cluster-wide `get` on Secrets when
the whole cluster is watched (owner's decision, ADR-024; list namespaces to
scope it), the same per namespace in namespaced mode, the ghcr.io registry
warning and the Dockerfile HEALTHCHECK rule (Kubernetes probes are used).
Info: the audit identity shown is the `email` claim; filtering by user ID
is exact.
